# 证据闭合与提交前复核

用于完成初稿后、提交归因 JSON 前的证据检查。同模型二次检查与独立验收分别记录。检查依据是当前 attempt 的原始材料与公共合同，不采用参考答案。先核对下列关系，再决定结果能否提交；无法闭合时保留未知及具体缺口。

## 逐项目标的证据

每个验收目标先写清对象、所需状态及判定依据，再填 status 和 evidence_ids。

- satisfied/unsatisfied 的 evidence_ids 必须实际链接到支持该目标状态的截图或执行回执。证据出现在整份报告的其他位置，不等于本目标已引用它；沿每个 ID 回查观察内容、对象身份、动作前后时序。
- 模块说“完成”、生成 click/answer 命令或计划执行某动作，只证明该模块的输出。生成 answer 不自动证明执行器已接受并交付答案；需要交付确认时，仅有生成日志就保留未知。
- 未满足也是状态判断，需要结果证据。错误页面、登录拦截等可作证据，但必须引用实际画面/回执，不能只引用 Reflector 对画面的自述。不要为满足检查任意添加一张无关截图。
- unknown 可表示证据不足，不能用没有找到成功画面直接推出 unsatisfied。存在真实回执时不额外要求截图；不得虚构缺失的回执。
- goals 只列原任务和公共任务口径的验收条件。Agent自行添加的检查、汇报或收尾，不自动成为目标；缺少这类步骤不自动抹掉已经证实的任务完成。若公共口径要求最终答复，区分译文等应用内目标与答复交付状态。

## 材料覆盖与处置

“全部现有文件已读取”与“完成判定所需材料充分”分开记录。逐一辨别缺口：文件确实缺失、内容不可读、实际传输被截断、还是该阶段可能本就不产生该文件。终止动作后没有 Reflector 不足以证明日志丢失；无运行规范或终止元数据时说明不确定，不补造文件存在性。

按当前输出合同，只要 missing/truncations 仍记录真实缺口，scan_complete 就不能为 true。原日志自身的重复/畸形文本应作为内容问题说明，不能谎称本次 API 传输截断。尚未完成全面复核时，保留已有 completion 证据，最终处置可用 pending；不得为取得 success 清空真实缺口。


## 因果解释与责任来源

预算浪费只能按已观察到的重试、绕路或零进展描述。估计的剩余动作数不是成功保证；“浪费了两步，剩余也只需两步”不能证明去掉错误后必然成功，尤其还涉及未验证对象、排序或未来页面行为时。主要根因应有实际偏离、后果及未恢复链条，不能仅凭步数相等选择。

分清原始模块输出、下发命令、解析/适配错误、执行回执与后续画面。只有下游报错或截断字符串、缺少原始输出时，可以确认可见的无效动作现象，但不能直接断定由模型生成、服务传输或适配器中的哪一层造成。候选中保留来源不确定性，不强填一个已确认责任模块。mapping gap 只用于模板没有对应标签，不用于掩盖取证不足；尚不能确认主要根因时按合同保留空归因和原因，已有独立证据支持的其他根因仍可报告。

## 提交的停止条件

完成全部规定材料检查后，做一遍目标、主要因果、来源及字段一致性的收尾检查；发现确定问题时集中做一轮针对修正，然后提交。仍无法闭合的事实标未知并写明限制，不继续循环改写同一份JSON、重复相同字段检查或增加无关证据。该停止条件不允许跳过原始材料或保留已知可修复的矛盾，更不授权编造字段；它约束分析收尾，不规定外部模型调用次数或工程重试政策。

## 最后一遍检查

1. 回查每个目标的 evidence_ids：存在、对象一致、时序正确，证据类型足以支持该状态。
2. 对照 coverage 与 outcome：缺口、完整扫描、成功处置没有互相矛盾。
3. 回查主要根因与恢复项：实际责任来源可追溯，说明没有依赖未经验证的“如果省几步就必成”。
4. 运行可用的 schema/模板/路径/回执校验。错误若涉及目标、证据或责任，回到材料复核；不足则保留未知，不改标签凑合通过。纯格式适配的原值和变更应另存。

机器校验通过只说明输出满足合同；它不认证事实理解或因果推断。未通过的输出保留原文及错误清单，不作为已验收结果提交。

提交前逐项回查原始证据，不能以自称已检查代替。locator仅描述source内区域/字段；若写明文件名或路径，须与source一致。外部调用方若另行安排模型复核或独立验收，应保留原始输出与修订记录，不将后处理过程伪装成本轮原始回答。

机器校验若指出证据或一致性问题，回查原材料；无法消除缺口时保留未知。答案交付不能由before_action截图、较早步骤的画面或module_output单独确立。调用重试政策由外部运行协议规定，不属于归因结论。

## 未完成结论与条件要求的证据门槛

先核实目标是否属于验收条件，再判断其状态。条件规则“只有需要向用户返回信息时才执行answer”不推出每项任务都必须答复；“查看、关注、点击”等应用操作也不自动要求额外汇总。仅当原始指令或已确认公共口径触发该条件时，才把答复交付列为独立目标。复核删除Agent自加目标时，在limitations记录被移除的goal ID、原条件及不适用原因；不能静默删除原任务真目标来消除错误。

未完成可由多项证据组成的动作链证明，不要求某一张截图单独证明历史上“没有做过”。核对以下条件：①相关对象与此前完成状态明确，已有过程记录未显示该子目标已完成；②最后计划把该子目标列为尚待执行，实际下发动作和操作后画面/回执证明最后只完成了前置操作；③本attempt在该步后确实终止，没有继续执行窗口。三者一致且无未解决的反证或相关动作缺口时，可以判unsatisfied，无需额外虚构一张“未执行证明”截图。

例如：已看第一项→计划返回列表再打开第二项→实际只执行返回→操作后仍在列表→已确认运行在此结束。这条链可证明本attempt未查看第二项。仅有“当前在列表”的孤立截图、仅有未完成计划、或仅缺少后续文件，则不足以形成同一结论；若早先已完成第二项或末步实际已打开它，也不能套用此推断。

完整性按该子目标的相关动作链判断，不把全局其他模块的无关缺口自动升级为本目标未知；但相关缺口、未对齐图片、后续动作可能仍在执行等必须保留。完成观察与终止原因分开：真实终止可由运行器记录、已知运行规则或任务提供者对本attempt的明确确认支持。用户补充的运行事实单独存档并说明来源，不能伪装成原始日志；只给出期待标签不构成终止事实。目录最高步号不自动等于max_steps。

若上述链条未闭合且没有其他直接反证，再保留unknown及缺口。若另一个必要条件已有直接不满足证据，可以据此判未满足，但要说明条件与目标的关系，不能任意挂图。

区分文件存在性、模块陈述和外部事实。manager/reflector的response不能重标为metadata或execution_result；运行终止、执行回执和动作清单应标明各自真实来源；外部补充确认应独立记录来源与适用attempt，不能改写原始日志。目录清单不等于运行器终止记录。证据类型由来源和内容决定，不由想证明的结论决定。

结构校验与证据验收分开记录。补齐截图引用只满足必要条件；独立复核必须联合核查状态、实际动作、相关历史与明确终止条件，不能把对孤立截图的限制误用于完整动作链。配套协议的acceptance.json在缺少独立证据复核时为contract_only；有哈希绑定的独立复核失败记录时必须隔离，即使结构错误为零。核查记录不得由待验收模型自证，任何验收状态变化均不改写原始模型结果。
