# 判定规则

任务完成、案例处置与原因分别判断。标签使用当前模板，不将项目分类声称为上游官方分类。

## 完成与处置是两件事

completion 记录 success / partial / not_completed / unknown；decision 记录 success / fail / rerun / precondition_blocked / pending。partial 表示部分目标完成，不是“部分成功即通过”。

| 情况 | 处理 |
| --- | --- |
| 对象、数量、约束和所需动作均有可靠完成证据 | success；Initial、Recovery 为 null |
| 已完成但模型仍检查 | 若未破坏目标或产生已确认的违规额外操作，仍可 success；记录过程效率问题，不机械判失败 |
| 明确过度操作，例如要求只加入 test 却实际同时提交其他歌单 | fail；必须确认额外状态变化确实发生，不能只凭面板勾选认定已经提交 |
| 超步后未完成 | fail；分析主要根因，不能填“30步不够”作为根因；证据无法确定原因时允许 Initial null 并写明缺口 |
| 适配器转换/支持错误直接导致未完成 | fail，正常归因；没有合适模块时留映射缺口，不因其是适配器问题就仅标待确认 |
| 目标状态被前序运行预先满足，影响本次执行 | rerun；针对指定对象恢复后重跑；旧 attempt 的独立错误仍可分析，新 attempt 的 GT 需重新标 |
| 环境没有所需内容、选项、权限或数据 | precondition_blocked；独立记录预置问题及模型是否正确处理，不伪装成已有 App 异常标签 |
| 完成与原因均受缺失/冲突证据影响 | pending；说明缺什么，不能当作无错误 |


目标预存但属于任务必要输入不算污染，例如“查看我的收藏”需要已有收藏。登录通常是正常前置。具体默认状态是否违规由任务验收条件决定，不把所有个性化状态都判污染。

## 验收条件来源

以原始指令、明确提供的任务约束及公共任务口径建立验收条件。条件式的answer许可或要求，必须先证明任务触发了返回信息的条件；不得把“只有需要时才答复”改成“所有任务必须答复”。模块Plan、历史记录和终止声明只反映Agent当时的理解，不能据此新增、收紧或替换用户目标。对每个判为未满足的验收项，应能指出它依据哪项原始要求或公共口径。

Agent自行安排的最终汇总、额外重开验证、记录标题等步骤，若任务本身不要求，未执行不直接构成任务失败；若用户确实要求回答、交付或核验，则按实际要求检查。终止声明可用于还原流程，不能单独代替业务目标证据。

检查对象来源与选择条件是否保持一致：页面显示某人、搜索给出某结果，不足以证明其满足指定平台、推荐来源、排序、数量或“最近”等约束。证据只能证明对象出现时，不将其擅自写成目标选择已正确。

## 预置问题

单独记录preconditions及模型应对；type使用模板中的预置类型机器ID：

- account_permission：账号／权限限制，包括登录、身份验证或功能受限
- insufficient_content：目标内容不足，所需作品等数量不足
- unavailable_option：指定功能／选项不可用，如目标画质不存在
- no_matching_result：无符合条件的结果，如精确筛选为空
- capacity_business_limit：容量／业务规则限制，如明确的收藏上限


Mobile-Agent和Agent-S2允许Initial精确映射为 `precondition → type → null`；L3留空是约定，不是映射缺口。纯预置根因的responsible_actor用precondition、stage用environment，不能伪造为Planner或Manager失误。error_candidates在此可记录有证据的阻塞候选，并不表示模型犯错。它需关联同类型、同步骤的confirmed preconditions。未知发现步骤或证据不足时不强填精确Initial。

预置存在不证明Agent无错。看到空结果仍选不满足约束的对象并宣称成功，记录独立模型错误，主要根因依证据选择，preconditions仍保留。所有框架的预置问题只作为Initial阻塞原因或独立preconditions记录，不作为Recovery根因。Recovery必须是模型后续独立的检测、诊断、策略、反馈采纳或执行缺陷；外部条件本身不可用不是恢复错误。

UniPath用Module=null、Function=E2、Mechanism=上述五类之一，Object选择已有的受限对象；无合适对象可null，不因此报映射缺口。stage=environment、responsible_actor=precondition，并关联同类型同步骤的confirmed preconditions。E2仅用于Initial，Recovery沿用R类且必须有独立模型恢复失败证据。服务异常仍用E1，不塞进预置问题。

运行器通信许可未放行导致的动作阻断，按当前项目运行规则标rerun，与真实适配故障分别处理。登录、身份验证及权限限制按以下边界处置：

- 需要人工完成登录/验证准备或针对性恢复容量，且已有明确重跑安排：decision=rerun，同时记录对应预置条件；不能自行虚构重跑安排
- 有证据表明账号缺少任务所需权限或资格，且当前准备步骤无法解决：decision=precondition_blocked，同时保留限制证据
- 未登录但是否能准备、是否安排重跑都未知：记录已确认的登录不足，处置保留pending并说明待确认事项，不假定永久无权限或已安排重跑
- 上游动作合法，但实际登录、权限操作或适配执行出现独立错误：根据证据正常归因；不能仅因发生在登录页就统归预置问题

重跑处置不抹掉已确认的限制或独立模型错误。真实适配支持/转换错误导致未完成仍按fail归因。

判预置根因前追查阻塞的来源：当前应用、账号、页面及对象是否与任务一致；到达该处的上游选择是否正确；阻塞是否确实限制了原任务的可行路径。若证据表明因选错应用、对象或路径才遇到限制，优先分析引入偏离的责任模块；错误路径上的真实登录墙可以记录，但不因此推定正确目标应用也受同一限制。若上游偏离已恢复、限制独立存在，或多因并存，按证据说明主次。身份或可行性无法核实时保留未知，不能因未看到入口便断言所有可行路径均被封锁。

同理，初始页面不符合模型预期，只能先记录初始可见状态；确认状态污染还需核对该状态是否在本次相关动作前已存在、是否违反所需基线、是否影响执行。不能仅凭非首页或模型称“恢复旧页面”就确认前序运行污染；来源未知须保留未知。

普通广告、正常业务限制、无匹配内容与App异常不同；临时没找到入口或页面被遮挡不能证明功能或内容不存在。

## 主要根因

问题来源假设、偏离语义和责任模块分开验证。先用原始目标与实际行为的差异描述原因，再查证谁输出了引入该偏离的要求或动作。初步来源可被后续证据推翻；同一语义错误可以发生在不同模块，不能将状态理解错误默认归Manager，或将选错对象默认归执行器。上游错误传播不自动变成下游独立错误，独立恢复责任需要新增观察/判断证据。

主要原因的选择至少交代它影响了哪个未完成目标、后续链条是否仍受其影响，以及其他有竞争候选为何解释力较弱。已恢复或无关的早期探索不能仅因发生早就占据主因；持续目标偏离也不能在缺少对象/来源证据时凭直觉优先。

选择主要导致本次失败的、证据最充分的因果节点。Initial 字段沿用模板名称，但不机械解释为“整条轨迹时间最早的错误”。

先检查目标一致性：按当前计划完成全部动作，是否仍违反原指令的应用、对象、来源或其他核心约束；不把Agent自行选择的目标当作已获用户认可。此检查只判断计划与验收条件的关系，不能据此虚构完成后的状态。再比较各候选是否造成持续阻塞、是否消耗可观察的无效步骤、是否已经恢复，以及后续失败是否沿该链发生。说明为何该候选比其他候选更能解释结果；不要求虚构概率或预算精确归因。

已恢复错误可以贡献预算损失，不能写成从此一直未纠正。不能仅凭发生最早、局部耗步最多或最后一个异常就选为主因；持续的目标偏离与局部绕路应比较其对原始验收条件的影响，不用估算“还差几步”替代因果证据。只有晚一步失败而没有前后证据，不反推早期根因。多因难分时保留主因选择限制，不声称唯一原因。secondary_causes 记录有独立证据的贡献项，不重复列上游错误的必然传播。

## Recovery

逐项填写 exists、step、evidence、attempted、outcome、reason：

- yes：错误后存在可观察异常，且 Agent 仍有观察/决策/执行机会
- no：如最后动作被运行器拒绝后立即终止，没有后续决策窗口；必须有终止/流程证据
- unknown：看不到后续观察或流程，无法判断是否有机会
- not_applicable：没有待恢复的任务错误，例如正常成功

attempted 与 exists 不等价；有机会但没发现或没行动也可能是恢复缺陷。recovery 只记录与 Initial 有因果联系的独立后续检测/诊断/策略/反馈采纳/执行错误。不得复制同一错误到两个栏位充数，不要求必须出现外部“正确反馈”才允许判断检测失败。

已成功恢复：outcome=succeeded，Recovery null。没有机会/未知：Recovery null 并说明。恢复错误步骤应位于机会出现之后或当步，且有可区分的观察/决策节点；如果与 Initial 同一步，需明确不同阶段，否则不要重复归因。

## 确定结论的材料要求

最终success须完成全部模块日志与图片的规定检查，确认后续未破坏目标或产生违规操作。已看到目标达成而后续材料未读，completion可记录success，decision保留pending。fail、rerun及预置阻塞也必须有对应结果证据；没有原始材料或只有无来源的结论文字，不能直接输出确定失败。结果失败已确定但主要原因尚无法确定时，可Initial=null并写明证据缺口，不虚构责任模块。

恢复机会、尝试及结果的取值组合以输出约定为准，exists=yes不能搭配attempted/outcome均not_applicable。
